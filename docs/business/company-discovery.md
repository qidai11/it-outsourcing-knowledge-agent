# Company Discovery — Task 0 模拟业务发现基线

> 状态：**SIMULATED_BASELINE / 待真实业务校准**  
> 版本：v0.1  
> 目的：在当前没有真实公司资料、真实项目文档和真实访谈记录的情况下，为 V1 工程实现提供一个明确、可测试、不会虚构生产接入的业务基线。

## 1. 真实性声明

本文件中的公司、客户、项目、人员、文档和工单均为模拟数据，不代表真实企业生产环境。

当前 **未完成** 以下真实业务动作：

- 未访谈真实项目经理；
- 未访谈真实开发/测试人员；
- 未访谈真实实施/支持人员；
- 未收集真实客户项目资料；
- 未接入真实 Jira、禅道、飞书项目或其他项目管理系统；
- 未获得真实线上流量、QPS、准确率、节省工时等业务指标。

因此，本 Task 0 只完成“工程可开发基线冻结”。后续拿到真实业务材料后，应以真实访谈结果替换本文件中的模拟假设，但不得改变 V1 已锁定的核心架构，除非形成新的 ADR。

### 2.1 模拟业务特征

假设公司具有以下典型特征：

1. 项目资料散落在共享文件夹、网盘、代码仓库和成员电脑中；
2. 同一个项目存在多个需求、接口、部署和测试版本；
3. 不同客户项目必须严格隔离；
4. 项目成员经常需要查询需求编号、接口路径、表名、错误码和版本上线步骤；
5. 历史问题主要通过人工搜索项目文档和工单记录定位；
6. 当前项目管理系统没有可供本实习项目调用的生产 API；
7. V1 只允许在 Sandbox 中验证工单查询、草稿、确认和幂等创建。

## 3. 公共知识域

### `company-public`

用途：

- 公司开发规范；
- 代码提交流程；
- 测试提交流程；
- 通用部署规范；
- 通用问题处理流程；
- 文档命名与版本规范。

默认规则：

- 公司内部有效项目成员可以读取；
- 公共知识不得包含任一客户的敏感项目事实；
- 公共知识不能覆盖项目级正式基线；
- 当公共规范与项目正式基线冲突时，以项目当前有效正式文档为准。

## 6. 模拟角色访谈代理需求

由于当前没有真实访谈，先用角色代理问题冻结开发需求。

### 项目经理关注

- 当前正式需求是哪一版？
- 某个变更是否已经被批准？
- 某个验收条件来自哪份正式文档？
- 上线前有哪些必须执行的步骤？
- 回答能否给出文件、版本和段落来源？
- 旧版、草稿是否会误作为当前依据？

### 开发 / 测试关注

- 某需求编号具体要求是什么？
- API 有哪些字段、必填项和错误码？
- 数据库表主键和关键字段是什么？
- 某个版本修复了什么？
- 某个异常是否有历史问题记录？
- 测试验收条件和边界值是什么？

### 实施 / 支持关注

- 客户环境部署步骤是什么？
- 配置项怎么填？
- 已知错误码如何处理？
- 是否有相似历史 Issue？
- 能否先生成工单草稿，再由人确认创建？
- 系统异常时是否会重复创建工单？

## 8. Task 0 当前结论

本阶段允许进入代码开发的前提是：

1. 明确所有当前业务数据均为模拟；
2. V1 固定内部使用；
3. 工单固定 Sandbox；
4. 两个模拟项目用于隔离测试；
5. 文档权威由人工维护；
6. 只有 PUBLISHED 文档可检索；
7. 任何真实业务成绩必须在后续实测后才能写入报告或简历。
